# ai-flow

Local orchestrator for one SZ ticket: it drives the `skills/sz-dev` workflow headlessly — resolve the workspace, run the four sz-dev phases with a configured agent, verify each gate's evidence through `sz-progress`, package the delivery, and stop at the single human gate.

This file is the guide for changing `ai-flow/` itself. It is not the workflow that implements an SZ. Stage order lives in `src/orchestrator.ts`; the sz-dev phase/gate state machine (`sz-progress`) is the single source of truth for run state, and `state.json` only mirrors it for the viewer. `skills/sz-dev/workflows/phaseN-*.md` are the agent's execution specifications; the orchestrator names the workflow file in each stage prompt and never lets the agent advance stages itself.

## Run

ai-flow is **Linux-only**: the run-lock stale detection reads `/proc/<pid>/cmdline`, stop/reset rely on `pkill`, and the ref-lock semantics assume POSIX. `src/cli.ts` fails fast on other platforms.

From the repository root, after `npm install` and `npm run build` inside `ai-flow/`:

```text
node ai-flow/dist/cli.js run SZ34623
node ai-flow/dist/cli.js status
node ai-flow/dist/cli.js ui
```

`npm run ai-flow -- run SZ34623` from `ai-flow/` runs the TypeScript sources without a prior build. The status page is served at the `ui.host`/`ui.port` set in `ai-flow.config.json`. It lists `.ai-flow/runs/`, can start a local run with **Create task**, can **Retry** a failed run from the failed stage, can **Approve** or **Reject** a run that is awaiting review (approve answers an open escalation, or passes gate 4 and downloads the package), can download the delivery tarball when `artifacts.package` exists, and offers a **Manage MCP** dialog (left of Create task) that edits the configured agent's MCP server list. It does not submit git or write back to the ticket system via softzilla. Manage MCP is operator-only: the human edits the agent's MCP config through the UI; the agent never modifies its own MCP list (that would break the isolation guarantees in the hard rules).

Run `node ai-flow/dist/cli.js init` (or `npm run ai-flow -- init` from `ai-flow/`) at the repository root. It asks which agent to use — Cursor, Claude Code, ChatGPT, DeepSeek, ZCode, or OpenCode — then which model, and writes `ai-flow.config.json`. Non-interactive: `ai-flow init --agent cursor --model composer-2.5 --yes`. The file stores `agent` and `model`; the command line for that agent lives in `src/agents.ts`. A file that only has the older `runner.command` array still runs, and a re-init preserves it (together with user-set `runner.modelFlag` / `modelsCommand` / `statusCommand` / `versionCheck`): a previous command counts as custom when it carries a prompt token, belongs to the same agent (or to a legacy file with no `agent` at all), and differs from the preset's own template (bin path aside); switching to a different agent never preserves the old command. Tokens in that command are `{promptStdin}`, `{promptArg}`, `{promptFile}`, `{cwd}`, and `{model}`. `runner.modelFlag` defaults to `-m`; `runner.modelsCommand` and `runner.statusCommand` are optional commands the viewer uses for the model dropdown and status bar. `szdev.skillDir` defaults to `skills/sz-dev`; `szdev.pack` is the fallback module pack when phase 1 does not record one. The ticket is fetched by the agent through its configured softzilla MCP — ai-flow no longer runs a separate MCP client, so there is no `mcp` config block. Do not commit cookies, and do not write them into `state.json` or logs (`src/redact.ts`). The status bar shows this agent and model. Token counts come from `runner.statusCommand` when it is set, and for an OpenCode preset from its local session database.

There is no `CURSOR_API_KEY` and no `@cursor/sdk`. Any headless agent is a local process started by `src/runner.ts`.

## Stages

`runPipeline` in `src/orchestrator.ts` stops on the first failure. Later stages become `skipped`. No package is written after a failed stage. Exit code `1` means the process never really started (missing config, missing command). Exit code `2` means a stage ran and failed.

| Stage | Who | Writes |
|---|---|---|
| `workspace` | Orchestrator: `sz-workspace ensure` (replay mode: `sz-replay init` at the pre-fix baseline) | `state.szdev` mode/workspace |
| `phase1` | Configured agent per `workflows/phase1-requirement.md` | `.sz-dev/SZ/phase1-requirement.md`, ticket caches, clarification comments |
| `phase2` | Configured agent per `workflows/phase2-implementation.md` | plan, code changes, `phase2-review.md`, gate-2 patch, handoff |
| `phase3` | Configured agent per `workflows/phase3-testing.md` | `phase3-test-plan.md`, `phase3-test-report.md` |
| `phase4` | Configured agent per `workflows/phase4-deliverables.md`, then the orchestrator packages | `deliverables/RN|TC|CN|IN`, `CHANGES-<SZ>.patch`, delivery tarball in `~/sz` |
| `review` | Stops: gate 4, the only human checkpoint | `state.json` status `awaiting_review`, `awaiting.kind = "gate4"` |

Gates 1-3 pass automatically once their evidence files exist (`sz-progress` enforces the evidence itself). Gate 4 is passed only by the viewer's approve action. An open escalation (`awaiting: E1-E7` in `sz-progress`) pauses the run as `awaiting_review` with `awaiting.kind = "clarification"` (E1) or `"escalation"`; the human's answer is recorded as `state.rework` on the current phase and injected into that phase's prompt on resume.

A later `run` of the same SZ resumes at the failed (or rework) stage; `sz-progress show` rebuilds the mirror first, so the sz-dev state survives even if `state.json` is stale. **Approve** on gate 4 sets `status` to `approved`, records gate 4 passed, and does not commit. **Reject** requires a phase (`phase1`–`phase4`) and a comment; the pipeline rewinds `sz-progress` to that phase (downstream gates reset) and appends the comment to the agent prompts.

Replay mode (the SZ's fix commit is already in git history) is decided by `sz-workspace ensure` in the `workspace` stage: the run then works in the replay tree at `fix-commit^`, diffs and packaging go through `sz-replay diff|verify|package`, and contamination checks run via `sz-replay audit`.

Replay mode enforces a **clean baseline project**. In the `workspace` stage the replay tree must end up a DETACHED, tracked-clean checkout of the pre-fix baseline: leftover tracked changes from a crashed prior run are restored to the baseline (the behavior `sz-replay init` documents for tree reuse), a branch HEAD or an unclean tree fails the stage, and an anchor mismatch between the tool (ensure/registry reuse) and ai-flow's own `findFixCommit` triggers an in-place re-anchor through `sz-replay init` when the detected fix is reachable in the tree (SZ34445 incident: a registry anchored on a harness commit that only mentions the ticket in its body put the fix itself into the "baseline"). The replay guard (`assertReplayNoOverreach`) runs after every phase: in phases 2-4 the HEAD must not move at all (the tree may carry the implementation); after phase 1 the tree must additionally still be tracked-clean (requirement-only phase). A HEAD move is legal in exactly one sanctioned case — the mid-Phase-1 replay switch (workflows/replay-mode.md "The switch") — and the guard checks its mechanical signature: DETACHED head, tracked-clean tree, and the new baseline is exactly the parent of a genuine fix commit for this SZ (`findFixChild`). A switch with all three signatures is ADOPTED, not failed: `state.baseCommit`/`szdev.baselineCommit`, the replay registry (`replay-SZxxxx.meta`) and progress.md's `meta base` are re-anchored to it, so every later phase and `sz-replay verify|diff|package` runs against the tree's real baseline. Any other HEAD move (an agent commit, a stray checkout, any phase 2-4 move) fails the phase as overreach. During the Phase-1 switch window the git ref-lock hook is NOT installed — the switch (and `sz-replay init`'s internal checkout) is itself a ref transaction the blanket hook would forbid; the end-of-phase clean-baseline guard is the enforcement there, and the hook still guards every other phase.

## Module adapters

`src/adapters/index.ts` defines the `ModuleAdapter` contract (scope guards, pack check, phase snapshots, reviewed-surface exclusions) and `getAdapter(module)` dispatch. `cqlAdapter` (same file) is the v1 implementation: phase 2 changes must stay under `cql/`, `.gitignore` and `.sz-dev/` edits are ignored, and the pack `check` capability runs `cql_lint.py` when present. `claimAdapter` (`src/adapters/claim.ts`) is the second implementation: the scope is the two VERIFIED claim roots from the pack's `domain/code-map.md` (`ehr/src/Charge/Claim/` frontend + `webframe/` backend), there is no module test area (phase-3 snapshots are strict), and the pack `check` is a manual track surfaced as a WARNING pass. A new module pack means a new `src/adapters/<module>.ts` plus a pack under `skills/sz-dev/references/<module>/` with the seven-row capability table.

Post-review code drift is guarded in standard mode via the adapter: phase 3 snapshots the change surface before the agent runs and `assertPhase3Scope` fails the phase if it moved; before packaging, phase 4 byte-compares the final tree's reviewed surface against the trusted gate-2 snapshot the orchestrator writes into the run dir (`gate2-reviewed.patch`, outside the agent's workspace). The reviewed surface is the adapter's `phase4Snapshot` — product code, with the module's test area excluded, because that area is allowed to evolve during phase 3 (`assertPhase3Scope` ignores it) and ships in the delivery tarball where the human audits it at gate 4. The agent-side gate-2 patch (`checkpoints/SZxxxx_gate2.patch`, which becomes the deliverable CHANGES patch) stays the full tree diff. Replay mode gets the byte-exact equivalent from `sz-replay verify`.

Upgrade note: `gate2-reviewed.patch` is written by whichever ai-flow version runs the pipeline. Runs that started on an older version (which snapshotted the FULL tree) keep working after an upgrade automatically: the orchestrator marks the surface it writes (`state.szdev.gate2Surface = "product"`), and a legacy full-tree `gate2-reviewed.patch` without the marker is narrowed to its product sections (`filterPatchToProductSurface`, driven by the adapter's `productSurfaceExclusions`) before the phase-4 byte-compare — phase-3 test-area evolution does not false-fail an upgraded run, so no reset is required.

The delivery tarball is written to `~/sz/SZ<id>_<Beijing timestamp>.tar.gz` (`SZ_PACKAGE_DIR` overrides the directory, used by tests). `.sz-dev/` state and pipeline runtime files are never packaged.

## Layout

- `src/cli.ts` — `init`, `run`, `status`, `ui`, `stop`, `reset`
- `src/config.ts` — `loadConfig`: preset expansion, legacy `runner.command` fallback, `{model}`-adjacency warning, `agentProcessPatterns` for stop
- `src/types.ts` — shared types: `RunState` (the `state.json` mirror, `rev` for optimistic concurrency), stage/sz-dev mirror, adapters, `AiFlowConfig`
- `src/errors.ts` — `StageError` (kind + exit-code mapping) plus `ConcurrentStateError` / `StateConflictError` for the state store
- `src/store.ts` — `state.json` mirror: atomic write (unique-name temp + rename, so the two writers never share a temp file), monotonic `rev` with refused stale writes, `withStateUpdate` retry wrapper
- `src/lock.ts` — per-run mutual-exclusion lock (`run.lock`), stale-lock reap, orphan-agent kill (the whole process group, `killAgentGroup` — the runner spawns agents `detached`, so the agent's own children die with it; legacy pid files without a group fall back to the single pid), live-pipeline refusal. Stale detection is tri-state (`probeAiFlowPipeline`): a live pid verified as an ai-flow pipeline is refused (unless `force`), a verified-foreign live pid is taken over, and an UNVERIFIABLE live pid (cmdline unreadable, e.g. kernel hidepid) is also refused unless `force` — it may be another user's live run, and reaping it would double-book the workspace
- `src/git.ts` — git helpers: diff/patch text, change lists, product-surface patch filtering
- `src/gitLock.ts` — `ai-flow-<ticket>` ref-transaction lock around the agent's ref writes (prevents the agent from moving refs out from under the pipeline); removed in the orchestrator's finally, and also by `stop`/`reset` from the run's workspace when a killed pipeline never reached that finally — a leaked hook would block the operator's own manual commits (a pre-existing user hook is backed up and restored byte-for-byte)
- `src/redact.ts` — strips cookies/tokens/Bearer secrets from text before it reaches `state.json` or logs. Every durable log surface is redacted at the write point: the runner's on-disk stage logs and the viewer's start log go through the line-buffered redactor (`createLineRedactor` / `RedactingLineTransform`), so a secret split across chunks is still caught; the operator console stream stays raw by design. The one surface written by the AGENT (its own session store, served by `/api/agent-session-log`) is redacted at the READ point, because no write-point redactor ever sees it
- `src/reset.ts` — `ai-flow reset`: removes run record, workspace, replay tree, wrapper, registry entry; also removes a leaked git ref-lock hook from the run's workspace (covers the config-missing fallback and a pipeline that crashed before the stop ran)
- `src/jsonFile.ts` — safe JSON readers (`readJsonSafe` / `readJsonObject`) shared by `mcp.ts` and `agents.ts`
- `src/streamFormat.ts` — stream-json (zcode) formatter + event collector shared by the live log and the viewer
- `src/agents.ts` — headless command presets for the six agents
- `src/mcp.ts` — operator-facing MCP server CRUD: per-preset config-file descriptors (`mcpDescriptors`, keyed by `format`: `generic` for Cursor/Claude; `opencode-v2` for OpenCode's nested `mcp.servers`; `codex-toml` for Codex's `[mcp_servers]` in `config.toml`; `dsh-cordis` for DeepSeek Harness's cordis-plugin inserts in `~/.dsh/profiles/headless/cordis.patch.yml`; `zcode` for ZCode's native `~/.zcode/cli/config.json` / `<repo>/.zcode/config.json` `mcp.servers`, where env/headers are `[{name,value}]` arrays). Each server carries an operator `enabled` flag (default true) that round-trips through the agent's native `disabled` field (`disabled: true` for generic/opencode-v2/codex-toml/zcode, `config.disabled` for dsh-cordis); `setServerEnabled` flips it without touching the rest of the config, and the viewer exposes it as a per-server toggle plus a form switch. Reads/merges/writes preserve agent-specific extra fields; OpenCode v1 files are migrated into the v2 `mcp.servers` shape on first write, DSH edits preserve comments/non-MCP entries in the YAML, and ZCode edits keep its strict per-server `name` field plus `headers`/`oauth`/`isolation`/etc.
- `src/init.ts` — `ai-flow init` menu; a re-init preserves a custom `runner.command` (prompt token + same agent/legacy + differs from the preset template, bin path aside) and the user-set `runner.modelFlag` / `modelsCommand` / `statusCommand` / `versionCheck`, logging a note when it keeps the custom command
- `src/orchestrator.ts` — stage order, gate evidence checks, `state.json` mirror, overreach guard (HEAD + MCP-config fingerprints; replay: the clean-baseline guard that adopts a sanctioned Phase-1 re-baseline and re-anchors state/registry/progress), run watchdog; a viewer Stop that wins a state-write race is preserved — the pipeline's catch re-reads the disk and defers to a record that is no longer "running" instead of clobbering the operator's stop with a stage failure
- `src/szdev.ts` — typed wrappers over `sz-workspace` / `sz-progress` / `sz-replay` + output parsers + pack capability table
- `src/runner.ts` — spawn the configured command (`detached`: the agent leads its own process group, so stop/reap can signal the group and the agent's own children die with it); records the live agent's pid in the run's `agent.pid` (removed on exit)
- `src/stop.ts` — shared `stop` logic: kill the recorded agent's process group (cmdline-verified against a reused/stale pid; legacy single-pid files fall back to the bare pid) plus the ticket-anchored CLI pattern, then remove the leaked git ref-lock hook from the run's workspace. Never uses an unanchored agent pattern, so it cannot kill other tickets' agents
- `src/prompts.ts` — the four phase prompts (each names its workflow file); phase 1 tells the agent to fetch the ticket through its configured softzilla MCP (tools `bug_info` / `bug_comments`)
- `src/package.ts` — Beijing-timestamp tarball to `~/sz` (fixed UTC+8 offset, no ICU/`Intl` dependency — avoids the `hour12: false` "24" midnight quirk in some ICU builds)
- `src/testStage.ts` — check-result parsing shared with the cql adapter
- `src/adapters/index.ts` — `ModuleAdapter` contract, cql adapter, `genericAdapter` (the documented fallback for packs without a dedicated adapter: no scope guard, no automatic pack check — the viewer surfaces such runs with a loud "no scope guard" warning), `getAdapter` dispatch
- `src/adapters/claim.ts` — claim adapter (two-root scope, strict phase-3 snapshots, manual-track check)
- `src/viewer/` — HTTP API and static host for the React page: `server.ts` (listen; `wireStartLog` wires the detached start spawn into a REDACTED `start-<id>.log` + the child pid into `start-<id>.pgid` — a disk error on the log drops the file and keeps the redactor draining, so a broken capture log can never back-pressure the pipeline into a stall), `routes.ts` (slim dispatcher) + `routes/` (per-domain handlers; **Create task** reports an immediate startup failure as soon as the recorded pipeline pid is dead, waits 5s without a recorded pid and up to 30s while the recorded pid is alive (`AI_FLOW_START_WAIT_MS` / `AI_FLOW_START_WAIT_MS_WITH_PID`), `guards.ts` (timing-safe token check, CSRF Origin guard for mutating requests — http/https Origins only — per-client rate limit `ui.rateLimitPerMinute`), `streamCache.ts` (byte-cursor incremental parse of the append-only stream logs), `configSafe.ts` (per-request config reload that tolerates a bad file), `apiTypes.ts`, `http.ts` (body limit + send; `docs()` is cached per run behind a stat fingerprint because the detail endpoint polls every 3s), `process.ts` (`spawnAsync`)
- `viewer-ui/` — React + MUI status page; `api.ts` (token in `sessionStorage`, Bearer/`?token=` fetch wrapper, 401 re-auth), `useActionDialog.ts` (action lock + error toast); `vite build` writes into `dist/viewer-ui/`
- `test/` — `npm test` from `ai-flow/`; the suite is type-checked first (`tsc -p tsconfig.test.json`, `src` + `test` together, `noEmit`)

Package manager: install and run with **npm** only (`npm install`, `npm run build`, `npm test`). Do not add a `packageManager` field and do not switch the project to pnpm/yarn; keep the npm scripts canonical.

## Hard rules

1. Do not `git commit`, amend, or push from the pipeline. A human submits after gate 4.
2. Do not comment on, change, or upload to the ticket system via softzilla. Fetch is read-only.
3. Do not put MCP cookies or login cookies in the repo, in `state.json`, or in error text.
4. The status page may start a local run, retry a failure, answer an escalation, approve gate 4 (download only), reject back to a chosen phase, download the package, and edit the configured agent's MCP server list via Manage MCP. It must not submit git or write back to the ticket system via softzilla. MCP edits are operator-only: the agent is never given a tool to add/remove/modify its own MCP servers, because that would let a run load arbitrary local commands as tools and break the isolation guarantees.
5. `sz-progress` is the only writer of phase/gate state. The orchestrator sets phases and gates 1-3; the viewer sets gate 4. Never bypass it with `--force`.
6. Keep module edits governed by the module adapter's scope guards (cql: inside `cql/`; claim: inside `ehr/src/Charge/Claim/` + `webframe/`). Tests use `-n` and must not use `-S`.
7. When changing stage behavior, update `test/pipeline.test.ts` or `test/units.test.ts` and run `npm test` in `ai-flow/`.
